# CRM Database Foundation & Migration (Task 04)

This document outlines the implementation of the PostgreSQL database foundation for the Telecom CRM, conforming strictly to the architectural constraints defined in Task 03 and Task 03.1.

## 1. Migration Mechanism
* **Tooling:** Custom Node.js script utilizing the `pg` client (`database/migrate.js` and `database/rollback.js`).
* **Reasoning:** Maintains isolation, avoids introducing heavy ORM/framework bloat just for DB migrations, and ensures operations run predictably.
* **Execution:** `node database/migrate.js` (up) and `node database/rollback.js <steps>` (down). Migrations are tracked in the `migrations_history` table.

## 2. Naming Conventions
* **Tables:** Singular, lowercase, snake_case (e.g., `tenant`, `party`, `individual`).
* **Columns:** Lowercase, snake_case (e.g., `tenant_id`, `created_at`).
* **Constraints:** Explicitly prefixed (e.g., `pk_party`, `fk_party_tenant`, `uq_party_tenant_id`, `chk_party_type`).

## 3. UUID Strategy
* **Implementation:** `UUIDv4` generated by PostgreSQL via `uuid_generate_v4()` from the `uuid-ossp` extension.
* **Reasoning:** Aligns with the Product Catalogue ecosystem. It acts as the default `id` for persistence entities to ensure global uniqueness and avoid exposing business volume sequences.

## 4. Tenant Architecture
* The `tenant` is the foundational platform entity.
* Created with `tenant_code` (UNIQUE), `name`, and `status` (CHECK constrained to ACTIVE/SUSPENDED/INACTIVE).
* It sits at the top of the hierarchy; all domain tables (like `party`) are scoped to a `tenant_id`.

## 5. Composite FK Pattern (Multi-Tenant Integrity)
* Parent tables enforce a composite uniqueness guarantee: `UNIQUE (tenant_id, id)`.
* Child tables reference parents safely using: `FOREIGN KEY (tenant_id, parent_id) REFERENCES parent(tenant_id, id)`.
* **Result:** Database-level prevention of cross-tenant data leaks. (Confirmed by Integration Test A).

## 6. Audit Column Strategy
* Base columns: `created_at` (NOT NULL, default NOW()), `updated_at` (NOT NULL, default NOW()), `created_by`, `updated_by`.
* **Update Strategy:** A shared database function `update_updated_at_column()` and `BEFORE UPDATE` triggers are used to automatically bump `updated_at` reliably. 
* Timestamps are stored as `TIMESTAMPTZ`.

## 7. Soft Delete Policy
* Soft deletes (`deleted_at TIMESTAMPTZ NULL`) are implemented on foundational root entities (`party`).
* **Active records query:** Requires `WHERE deleted_at IS NULL`.
* **Subtype cascading:** We rely on the parent `party.deleted_at` to mark the logical entity as deleted, avoiding duplicated `deleted_at` columns on 1:1 extensions like `individual` and `organization`.

## 8. Party Inheritance Model
* Base `party` table containing `party_type` (CHECK constrained).
* Strict 1:1 extension tables (`individual`, `organization`).
* **Subtype Integrity Strategy (Phase 1):** Uniqueness constraints `UNIQUE (tenant_id, party_id)` on the extension tables prevent a party from having multiple individual or organization extensions (Confirmed by Integration Test D). Strict cross-table subtype validation (preventing an `INDIVIDUAL` party from getting an `organization` extension) is delegated to the Application Transaction boundary for Phase 1 to avoid fragile cross-table trigger deadlocks.

## 9. Index Rationale
* `idx_party_tenant`: Optimizes fetching a party by `(tenant_id, id)`.
* `idx_party_type`: Optimizes listing parties by type within a tenant.
* `idx_active_party`: A partial index `WHERE deleted_at IS NULL` to speed up active party lookups.
* `idx_individual_last_name`: B-Tree index for sorting/searching individuals.
* `idx_org_legal_name`: B-Tree index for organizational searches.

## 10. Rollback Approach
* Every `.sql` migration in `database/migrations/` has a strictly paired `_down.sql` script in `database/rollbacks/`.
* Running `node database/rollback.js` executes the down scripts in reverse order, cleaning up triggers, tables, and extensions cleanly.

## 11. Test Coverage
Database integration tests (`database/tests/db_integration.test.js`) are implemented and pass:
* **Test A:** Tenant isolation (Cross-tenant FK violation) -> Passed.
* **Test B:** Party type validation (CHECK CONSTRAINT VIOLATION) -> Passed.
* **Test C:** Tenant uniqueness (UNIQUE CONSTRAINT VIOLATION) -> Passed.
* **Test D:** 1:1 subtype relationship (UNIQUE CONSTRAINT VIOLATION) -> Passed.
* **Test E:** Soft delete behavior (Row remains, active query filters out) -> Passed.

All constraints and behaviors behave entirely at the database level, requiring no application logic to enforce.
